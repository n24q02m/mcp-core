## 2025-05-21 - Open Redirect Vulnerability in Relay Login
**Vulnerability:** Open Redirect in `relay-login.ts` and `relay_login.py`. The `next` redirect parameter was not validated before being used to redirect the user after a successful login. An attacker could craft a URL like `?next=//malicious.com` to bypass the `startsWith('/')` check (if it existed) or simply pass a full URL to redirect a user to a malicious site after authentication.
**Learning:** During authentication flows, redirect URLs passed as query parameters or POST body data (e.g., `next`) must be rigorously validated. A missing or insufficient validation (like only checking `startsWith('/')`) allows protocol-relative URLs (`//example.com`) which browsers treat as valid cross-origin redirects.
**Prevention:** Always validate that the `next` redirect parameter strictly starts with a single forward slash (`/`) and not a double slash (`//`) before issuing a redirect response. Default to a safe internal path like `/authorize` if validation fails.
## 2026-05-28 - Enhanced Open Redirect Validation in Relay Login
**Vulnerability:** Open Redirect in `relay-login.ts` and `relay_login.py`. The `next` parameter was only checked to not start with `//`, `/\ `, or `\\`, but could still be bypassed by a following whitespace or control character (e.g., `/ google.com`) which some browsers might normalize into a protocol-relative URL.
**Learning:** Checking the prefix is not always sufficient if browsers perform normalization. Whitespace or control characters immediately following a leading `/` can sometimes lead to a protocol-relative redirect.
**Prevention:** Validation of `next` parameters should ensure it starts with a single `/` AND that the second character (if present) is not a second slash, a backslash, or any whitespace/control character (ASCII <= 32).
